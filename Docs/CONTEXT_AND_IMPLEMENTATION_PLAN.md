# BillDesk Native Desktop — Context and Implementation Plan

## 1. Executive Summary & Context

### 1.1 Project Background
**BillDesk** (also referred to as **SV Billing**) is a specialized mandi / wholesale produce billing, inventory, procurement, receivables/payables, banking reconciliation, and double-entry accounting platform designed for fast-paced commercial trading environments.

### 1.2 Core Architectural Directive: Use Pre-Existing Collections Only
> **MANDATORY SYSTEM DIRECTIVE:**  
> The target MongoDB database (`sv_billing`) **already contains all necessary collections, indexes, and historical data** generated by the existing system.  
> **The native application must strictly use the existing collections and MUST NOT create any new collections, drop collections, or run collection-generating migrations.**  
> All services, repositories, and models must attach and bind directly to the pre-existing collections in `sv_billing`.

### 1.3 Legacy Architecture Analysis (`sirajpasha/BillDesk`)
The reference repository ([sirajpasha/BillDesk](https://github.com/sirajpasha/BillDesk.git)) represents a multi-tier web application packaged inside a desktop wrapper:
- **Frontend:** Next.js (React), TailwindCSS, custom server legacy proxy.
- **Backend:** FastAPI (Python 3.10+), Beanie ODM (asynchronous Motor driver for MongoDB), Pydantic v2.
- **Desktop Wrapper:** Electron / PyWebView opening a localhost web page interacting with FastAPI endpoints over HTTP.
- **Data Store:** MongoDB (`sv_billing`), containing 30+ pre-existing collections.

**Key Issues with the Legacy Setup on Mandi Counter Terminals:**
1. **Unnecessary Runtime Overhead:** Running Node.js/Electron, a Python web server (Uvicorn/FastAPI), and Chromium consumes significant memory and CPU on standard counter PCs.
2. **Network/HTTP Latency:** In-process desktop actions incur serialization, HTTP round-trips, connection timeouts, and web session management overhead.
3. **Multi-Process Fragility:** If either the FastAPI backend or the Electron renderer crashes or becomes out of sync, the terminal fails.
4. **Desktop Disconnect:** Browser-based UI lacks the responsiveness, precise modal dialogs, and reliable F-key keyboard-first navigation demanded by billing clerks.

### 1.4 Target Native Architecture (PRD Specification)
As specified in [BillDesk-Native-Desktop-PRD.md](file:///c:/Users/PashaLOQ/Downloads/BillDesk-Native-Tkinter-27018/desktopapp_native/Docs/BillDesk-Native-Desktop-PRD.md):

```text
│   (Keyboard-first, F1-F12 shortcuts, Treeviews, Dialogs)    │
└──────────────────────────────┬──────────────────────────────┘
                               │ In-process method calls
                               ▼
┌─────────────────────────────────────────────────────────────┐
│                  Application Service Layer                  │
│    (Business rules, calculations, validation, invariants)   │
└──────────────────────────────┬──────────────────────────────┘
                               │ Query / Command execution
                               ▼
┌─────────────────────────────────────────────────────────────┐
│                  Repository Layer (PyMongo)                 │
│      (Direct binding to pre-existing sv_billing collections) │
└──────────────────────────────┬──────────────────────────────┘
                               │ Direct MongoDB wire protocol
                               ▼
┌─────────────────────────────────────────────────────────────┐
│             Pre-Existing MongoDB Collections                │
│    (Local port 27018 / Standalone or MongoDB Atlas Cluster) │
└─────────────────────────────────────────────────────────────┘
```

**Key Architectural Tenets:**
- **Zero Collection Creation:** The application binds strictly to the existing 30+ collections in `sv_billing`. No `create_collection()` calls, no schema migrations altering collection topology.
- **No Web Runtime:** No FastAPI, Uvicorn, Next.js, Node.js, Electron, or PyWebView.
- **Direct PyMongo Driver:** In-process synchronous database operations with explicit session management for transactions (supported on replica sets / MongoDB Atlas, with ordered transactional fallback on standalone local MongoDB).
- **100% Schema & Data Compatibility:** Seamlessly reuse existing `sv_billing` MongoDB collections, field names, and documents.
- **Service Layer as the Primary Testing Seam:** All business rules (tax, discount, commission, credit checks, inventory deduction, ledger journal balancing) live in pure Python services, independently unit-tested without launching GUI windows.

## 3. Core Subsystems & Service Responsibilities

### 3.1 Authentication & RBAC Service
- **Login Verification:** Uses `bcrypt` to match passwords against `password_hash` in the existing `users` collection.
- **Security Hardening:** Strictly disallows reading or displaying plaintext passwords (`password_plain` stripped). Mask secrets in logs.
- **Session Identity:** Thread-safe in-process `CurrentUser` state (no JWT needed).
- **Authorization Engine:** `RBACService.can_access(user, permission_slug)` evaluates `role_permissions` menus, giving full wildcard `*` to `admin` / `super admin`.

### 3.2 Master Data & Pricing Services
- **ItemService:**
  - Create / update items with unique validation for `item_id` and `item_alias` in the existing `items` collection.
  - Fast search by alias prefix or regex.
  - Active/inactive filtering and safe soft-delete verification (block delete if referenced by active bills).
- **CustomerService & SupplierService:**
  - Complete address tracking (delivery vs bill-to) in existing `customers` and `suppliers` collections.
  - GSTIN format validation and PAN capture.
  - Credit limit checks: `current_balance + new_bill_amount <= credit_limit` (with `credit_limit == 0` signifying unlimited credit).
- **PricingService:**
  - Hierarchy: Active Fixed Price (`fixed_prices` valid between `start_date` and `end_date`) > Default rate.
  - Clearly flags in UI when a rate is fixed-contract sourced.

### 3.3 Billing & POS Engine
- **Keyboard-First Workflow:**
  - `F1`: Dashboard
  - `F2`: Save Bill
  - `F3`: Save & Print Invoice (PDF)
  - `F5`: Customer Search Popup
  - `F6`: Park Current Bill
  - `F7`: Recall Parked Bill
  - `F8`: Smart Importer
  - `F10`: Item Master
  - `F11`: Customer Master
  - `F12`: Logout
- **Atomic Save Operation:**
  1. Validate line items, prices, and customer credit limit.
  2. Reserve sequential invoice number `YYYYMMDD-XXXX` (daily reset) from existing `bills` collection.
  3. Persist `Bill` record into existing `bills` collection.
  4. Deduct stock using atomic PyMongo `$inc: {"stock": -qty}` in existing `items` collection and create `StockTransaction` in existing `stock_transactions` collection.
  5. Increment customer balance: `$inc: {"current_balance": total_amount}` in existing `customers` collection.
  6. Track crate movements in existing `customers.crate_balances` and existing `crate_transactions`.
  7. Post double-entry GL journal entry in existing `journal_entries` collection (`AR 1200 Debit`, `Sales 4000 Credit`).
  8. Write `BillAudit` entry into existing `bill_audits` collection.
- **Bill Void & Correction:**
  - Full financial reversal: Restores item stock, reverses customer balance, reverses crate count, and posts GL reversal journal into the existing collections.

### 3.4 Orders, Consolidation & Order Matrix
- **Order Lifecycle:** `pending` -> `confirmed` -> `delivered` -> `billed` using existing `orders` collection.
- **1-Click Conversion:**
  - `convert_to_bill`: Generates invoice in `bills`, decrements stock in `items`, updates customer balance, links `order.linked_bill_ids`.
  - `convert_to_purchase`: Generates purchase order in `purchase_orders` / `purchase_bills` for suppliers to fulfill demand.
- **Order Matrix:**
  - Cross-tabulated matrix: Rows = Items, Columns = Customers, Cell = Demand quantity.
  - Total demand compared with live stock in `items` collection to highlight shortfalls in red.

### 3.5 Inventory & Mandi Operations
- **Stock Tracking:** Real-time visibility of warehouse quantities from existing `items` collection.
- **Adjustments & Waste:**
  - Manual stock count reconciliations logged to existing `stock_transactions`.
  - Produce waste logging into existing `waste_logs` collection with financial loss categorization.
- **Crate Management:** Mandi returnable crate tracking across both customers and suppliers with net balance calculations in existing `crate_transactions`.

### 3.6 Procurement & Vendor Management
- **Purchase Orders (PO):** Documenting planned purchases in existing `purchase_orders` collection.
- **Goods Receipt Note (GRN):** Physical receipt verification with automatic inventory stock addition in existing `grns` collection.
- **Purchase Bills:** Vendor invoice recording in existing `purchase_bills`, TDS calculation under applicable sections (e.g., 194C, 194J), and AP liability booking.
- **3-Way Matching:** PO qty >= GRN qty >= Vendor Bill qty.

### 3.7 Accounts Receivable, Accounts Payable & Banking
- **AR Aging:** Buckets calculated dynamically from existing `bills`: Current, 1–30, 31–60, 61–90, 90+ days past due date.
- **Payment Receipts:**
  - Recorded in existing `payments` collection.
  - Modes: Cash, UPI, NEFT/RTGS, Cheque.
  - Allocation strategies: Automatic FIFO, manual invoice selection, or advance unallocated holding.
- **AP Payments:** Supplier payment tracking in existing `ap_payments` collection with net payout after TDS deduction.
- **Banking & BRS:**
  - Bank accounts in existing `bank_accounts` collection.
  - Bank statement CSV parsing into existing `bank_statements` collection.
  - Internal bank transactions in existing `internal_bank_transactions` collection.
  - Comprehensive Bank Reconciliation Statement (BRS) calculation.

### 3.8 General Ledger & Financial Statements
- **Double-Entry Bookkeeping:** Every transaction creates balanced `JournalEntry` records in existing `journal_entries` where `sum(debits) == sum(credits)`.
- **Chart of Accounts:** Read and update balances in existing `accounts` collection.
- **Financial Statements:**
  - **Trial Balance:** Verifies total debits = total credits across the existing `accounts`.
  - **Profit & Loss (P&L):** Income accounts minus Expense accounts for any date range.
  - **Balance Sheet:** Assets = Liabilities + Equity verification.

### 3.9 Printing Engine (ReportLab)
- Pure Python PDF generation (no browser printing or headless Chrome).
- Formatted specifically for Indian produce trade:
  - Formatted currency (`₹ XX,XX,XXX.XX`).
  - Total amount in words (Indian numbering system: Lakhs / Crores).
  - Clean layout: Company header, GSTIN, Customer details, tabular items with units, mandi fee/commission summary, and signature block.
  - Invoice PDF, Customer Ledger Statement, Day Book, and Purchase Orders.

## 6. Financial & Operational Verification Invariants

| Category | Invariant Rule | Verification Mechanism |
|---|---|---|
| **Database Integrity** | **Zero Collection Creation:** Strictly bind to pre-existing collections in `sv_billing` | Handled via direct repository collection binding; no `create_collection()` calls permitted |
| **Accounting** | $\sum \text{Debits} == \sum \text{Credits}$ for every Journal Entry | Enforced on every journal entry save; raises `ValueError` if unbalanced |
| **Accounting** | $\text{Assets} == \text{Liabilities} + \text{Equity}$ on Balance Sheet | Verified via Trial Balance and Balance Sheet generation tests |
| **Sales** | Invoice numbers must be strictly sequential & unique per day | Atomic sequence resolution query; unique index on `invoice_no` |
| **Sales** | Sales Return quantity $\le$ Original Billed quantity | Enforced in `SalesReturnService` validation |
| **Inventory** | Stock Count $\approx$ $\sum$ Stock Transactions | Reconciliation routine checks current stock against historical log |
| **AR** | Payment Allocations $\le$ Invoice Balance Due | Checked before allocating; invoice balance never goes negative |
| **Security** | Zero plaintext passwords stored or returned | Passwords hashed with bcrypt; `password_plain` excluded from models |

## 7. In-Depth Field Mutation & Cascading Effects Testing Framework

The system mandates comprehensive field mutation testing ensuring that when any single source field is altered, every direct dependent field and every cross-collection cascading side-effect is asserted and validated:

### 7.1 Field Mutation Dependency Matrix

| Domain | Mutated Source Field | Direct Dependent Fields Recalculated | Cross-Collection Cascading Side Effects |
|---|---|---|---|
| **Billing** | `line.qty` | `line.amount = qty * rate`<br>`bill.total_amount`<br>`bill.balance_due` | `items.stock` decreased by `qty`<br>`stock_transactions` entry logged<br>`customers.current_balance` increased<br>`bill_audits` created |
| **Billing** | `line.rate` | `line.amount`<br>`bill.total_amount`<br>`bill.balance_due` | `customers.current_balance` updated<br>`items.stock` quantity remains unchanged |
| **Billing** | `commission_rate`<br>`mandi_fee_rate` | `bill.commission_amt`<br>`bill.mandi_fee_amt`<br>`bill.total_amount` | `customers.current_balance` updated with total including fees |
| **Billing** | `crates_issued`<br>`crates_returned` | Net crate count | `customers.crate_balances[crate_item_id]` incremented/decremented<br>`crate_transactions` logged |
| **Billing** | `bill.status = "void"` | Status updated to `"void"` | `items.stock` restored (+qty)<br>`customers.current_balance` decreased (-total)<br>`customers.crate_balances` restored<br>`bill_audits` logged |
| **Payments** | `payment.amount` | `payment.allocations`<br>`payment.allocation_status` | `bills.balance_due` decreased<br>`bills.status` (unpaid -> partial -> paid)<br>`customers.current_balance` decreased |
| **Orders** | `order.items[i].qty` | `item.amount`<br>`order.total_amount` | Matrix demand and stock shortfall indicators updated |
| **Orders** | `convert_to_bill()` | `order.status = "billed"`<br>`order.linked_bill_ids` | `bills` created<br>`items.stock` decreased<br>`customers.current_balance` increased |
| **Procurement** | `supplier.tds_rate` | `purchase_bill.tds_amount`<br>`purchase_bill.payable_amount`<br>`purchase_bill.balance_due` | `suppliers.current_balance` increased by net payable<br>`journal_entries` balanced with TDS liability line |
| **Procurement** | `grn.items[i].qty` | GRN line quantity | `items.stock` increased (+qty)<br>`stock_transactions` logged (`type="purchase"`)<br>`purchase_orders.status` updated |
| **Inventory** | `stock_adjustment.qty` | Adjustment record | `items.stock` updated by signed qty<br>`stock_transactions` logged (`type="adjustment"`) |
| **Inventory** | `waste_log.qty`, `rate` | `waste_log.amount = qty * rate` | `items.stock` decremented<br>`stock_transactions` logged (`type="waste"`) |
| **Pricing** | `fixed_prices.rate` | Active price cache | New bills resolve to new rate; historical bills unaffected |
| **Sessions** | `cash_bill` / `cash_payment` | `session.expected_cash` | Expected drawer balance accumulated |
| **Sessions** | `session.actual_cash` | `session.difference = actual - expected` | `session.status = "closed"` |
| **General Ledger**| `journal_line.debit/credit`| Journal entry balance check | Must satisfy $\sum\text{Debits} == \sum\text{Credits}$; rejected if unbalanced |
